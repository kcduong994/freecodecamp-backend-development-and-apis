# Build JWT Protected Routes

**freeCodeCamp — Back-End Development and APIs**  
**Workshop 10 | Official freeCodeCamp completion: 36/36 | November 8, 2026**

## Overview

An educational Node.js/Express 5 REST API implementing JSON Web Token (JWT) authentication, role-based authorization (RBAC), and an in-memory token denylist. Users can register with a hashed password, log in, request their profile with a Bearer token, and log out. An administrative endpoint requires an `admin` role and strips `passwordHash` from the returned user records.

**Evidence:** freeCodeCamp course screenshot confirms **36/36 complete**; Codespaces and Windows terminals confirm server startup on port `8800`. Windows local integration reported **7/7 PASS** and `npm.cmd audit --omit=dev` reported **0 vulnerabilities** (November 8, 2026). GitHub publication must be verified separately.

> Educational implementation, **not production-ready authentication**. User records are stored in a local JSON file; the logout denylist lives only in process memory. JWT role claims are trusted until expiry, with no live database check for role revocation.

## Requirements and setup

- Node.js **20.11+** (or a newer maintained LTS release), npm and Windows PowerShell.
- Run commands inside `workshops/build-jwt-protected-routes`.

Install dependencies exactly as pinned in the copied lockfile:

```powershell
npm.cmd ci
```

Create `data/users.json` from the safe template if the file does not already exist:

```powershell
Copy-Item data/users.example.json data/users.json
```

Generate a new random JWT secret in the **local** `.env` (this deliberately avoids printing the secret):

```powershell
node -e "const fs=require('node:fs');const c=require('node:crypto');fs.writeFileSync('.env','PORT=8800\nJWT_SECRET='+c.randomBytes(32).toString('hex')+'\n')"
```

Do not overwrite an existing `.env` containing a real key unless deliberately rotating it. Never commit `.env`, `data/users.json`, or `node_modules`.

## API endpoints

| Method | Path | Requirements | Expected behavior |
|---|---|---|---|
| `GET` | `/` | None | Service health JSON, HTTP 200 |
| `POST` | `/api/auth/register` | JSON `email`, `password` | New user, bcrypt password hash, HTTP 201 and JWT; HTTP 400/409 for invalid/duplicate inputs |
| `POST` | `/api/auth/login` | JSON `email`, `password` | HTTP 200 and JWT if valid; HTTP 400/401 otherwise |
| `GET` | `/api/auth/profile` | `Authorization: Bearer <token>` | JWT payload in `{ "user": ... }`, HTTP 200; unauthorized HTTP 401 |
| `POST` | `/api/auth/logout` | Valid Bearer JWT | Adds token to in-memory denylist; future reuse HTTP 401 |
| `GET` | `/api/admin/users` | Valid Bearer JWT with `role: "admin"` | HTTP 200 `{ "users": [...] }` without `passwordHash`; ordinary user HTTP 403 |

## Implementation details

1. **User data:** `utils/db.js` reads and writes the JSON array in `data/users.json`, and provides `findByEmail()` and `findById()`.
2. **Password hashing:** `bcryptjs` hashes passwords with a work factor of 10; login compares submitted password to the stored hash. Plain-text passwords must never be persisted.
3. **JWT:** `jsonwebtoken` signs payloads including `id`, `email` and `role` using `process.env.JWT_SECRET`; token expiry is `1d`.
4. **Authentication:** `authenticate.js` checks Bearer format, in-memory denylist, token validity, and assigns the decoded payload to `req.user`.
5. **Authorization:** `authorizeRole('admin')` rejects missing or mismatched roles with HTTP 403.
6. **Error handling:** Express 5 forwards errors from asynchronous handlers to the four-argument error middleware, which returns an error status and `{ "error": err.message }`.
7. **Logout:** `blacklistToken()` adds the raw token to a module-level Set; `isBlacklisted()` prevents reuse while the process remains alive.

## Security boundaries and known limitations

- The denylist is lost on restart and is not shared between processes; production needs persistent, TTL-bounded revocation storage or an equivalent token/session strategy.
- Role claims inside an already issued JWT may become stale. Production authorization should check currently authorized privileges server-side.
- Local JSON-file persistence is not concurrency-safe and has no real transaction/locking scheme.
- Input validation, password policies, login rate limiting, secret rotation, HTTPS, cookie/CSRF policy where relevant, structured security logs and data-protection design need additional work for production use.
- The admin JWT used in the local test is signed **inside the local test process** using the local development key; this is a deterministic authorization test, **not** a production procedure for generating privileged accounts.
- In this curriculum's required error handler, raw `err.message` is returned. A deployed service should avoid leaking internal error details.
